# M3 结论

状态:**定稿**(2026-11-06,用户确认)· 对应设计文档 §11 的 M3:Android 真机,同一套代码在 Pixel 6a 上正确播放,并记录性能基线。
设计决定、差异和方法见 [m3-notes.md](m3-notes.md);原始数据见 [m3-bench-results.txt](m3-bench-results.txt)(设备上日志里 `ALPHACLIP_BENCH` 开头的那几行)。

## 一句话结论

**M3 的完成标准在下面这个范围内达成:Android arm64 + 一台 Pixel 6a(Android 15)+ Unity 2022.3.62f2 的开发构建。**
核心库有了 Android 版 `libalphaclip.so`(strip 后 680,520 字节,只导出 14 个 `ac_*`,所有 LOAD 段 16 KB 对齐),Unity 包把它当 Android ARM64 插件导入,
APK 在真机上从包里的 StreamingAssets(`UnityWebRequest`)读出两个样本片并循环播放:6 次、每次 10 秒,**一帧都没丢**,日志里没有 Unity 的错误或警告,没有崩溃。
设备上渲染出的 `Output` 与 Windows 编辑器里的同一帧在 6 组取样(共 864 个通道值)上**最大只差 1 个灰度级**。
性能基线(640×360、30 fps 的合成片,**没有固定核**):核心解码线程 **4.7 ms/帧(不透明)、6.3 ms/帧(alpha 片)**,主线程每个 Unity 帧在 `Present` 里花 **约 0.22 ms**。
**没有的:** Unity 6 上的 Android、AAB / Google Play 的 16 KB 检查、16 KB 页的设备、固定核类型的数、GPU 侧耗时、屏幕上最终画面的读回、真实素材和更高分辨率,详见"没覆盖到的"。
你选择按现状定稿,没有先补做剩余项(尤其是 Unity 6000 和 AAB 检查);它们记在"给后续的交接"里,不阻塞 M4,也不要当作已经做过。

## 数字(性能基线)

条件:Pixel 6a,Android 15,开发构建,Vulkan,电量 100% 接着线,电池温度开跑前 29.3 °C、跑完 29.2 °C;640×360、30 fps 的合成片循环播放,
主线程 `targetFrameRate = 60`、不等 vsync;**应用在安卓调度器下的实际表现,没有固定核**;每格是 3 轮的(最小 .. 最大)。

| | 不透明片 | alpha 片(解两路码流,只渲染彩色) |
|---|---|---|
| 核心解码线程 ms/帧(含彩色、alpha、平面拷贝,不含等待) | 4.66 .. 4.75 | 6.27 .. 6.37 |
| 主线程:上传三个平面,ms/张画面(CPU 侧) | 0.23 .. 0.24 | 0.23 .. 0.24 |
| 主线程:绘制提交,ms/张画面(CPU 侧) | 0.13 | 0.13 .. 0.15 |
| 主线程:取帧,µs/次 | 29.9 .. 37.3 | 30.6 .. 37.8 |
| 主线程:`Present` 合计,ms/Unity 帧 | 0.22 .. 0.23 | 0.22 .. 0.24 |
| Unity 帧时间 p50 / p95 / p99 / 最大,ms | 17.30 / 17.41–17.45 / 17.52–17.63 / 17.6–17.8 | 17.30–17.31 / 17.41–17.43 / 17.50–17.55 / 17.6–17.9 |
| 第一张画面,ms(从 `SetActive` 起,含从 APK 读文件、打开、解第一帧) | 32.6 .. 35.4 | 33.6 .. 35.0 |
| 画面落后时钟 p50 / p95,ms | 16.3–17.0 / 31.4–32.1 | 16.1–17.0 / 31.3–32.2 |
| 呈现 / 解出 / 丢弃 的帧数(10 秒) | 300 / 300 / 0 | 300 / 300 / 0 |
| Unity 分配器、图形驱动、Mono 内存 | 33.7 MB、40.6 MB、0.5–1.5 MB,每次运行都不变 | 同左 |
| 进程 RSS(粗) | 302 → 318.6 MB,峰值 319.0 MB;**最后三次运行峰值不再上涨** | |

怎么读这些数字:
- **解码有余量:** 30 fps 每帧预算 33 ms;一个解码线程占 14%(不透明)到 19%(alpha)。alpha 比不透明多约 **34%**(M1 在固定核上量到 39–44%,范围吻合,这里的噪声更大)。
- **解码数比 M1 的固定核数慢:** M1 在固定到小核 Cortex-A55 上量到 3.18 ms(不透明)和 4.58 ms(alpha)的中位数,这里 4.7 和 6.3,约 1.4–1.5 倍;
  比 M1 的中核(1.60 / 2.28)慢近 3 倍。**推断(没有量到):** 解码线程占空比只有 14–19%,安卓调度器很可能把它放在小核上、且是比最高频低的频率;
  这次没有记录运行期间线程在哪类核、什么频率(见 m3-notes 第 12 条)。所以这组数应当读作"应用不做特殊处理时的实际数",不是某类核的上限或下限。
- **主线程开销很小:** `Present` 每个 Unity 帧 0.22 ms,约占 17.3 ms 帧时间的 1.3%;每张新画面上传加绘制提交共约 0.37 ms(CPU 侧)。这是**提交时间,不是 GPU 时间**。
  M2 笔记里"若 M3 基线显示 RenderTexture 这一遍绘制或这张贴图成问题再改"——在 640×360 下没有问题,不需要改;**没有外推到 1080p**(像素数是 9 倍,耗时是否按像素线性增长没有量过)。
- **"画面落后时钟"不是延迟:** 对 30 fps 的片子,"取 pts ≤ 时钟的最新帧"本来就会落后 0–33 ms(均匀分布,中位数 16.7、95 分位 31.7),实测与之吻合,说明没有额外的排队延迟。
- **首帧:** 从激活物体到第一张画面 33–35 ms,约两个 Unity 帧,包括读 APK、打开和解第一帧。时钟从打开完成之后的下一次 `Update` 起算,所以起始处最多丢掉这个数量级的一段(≤ 约 1 帧的 30 fps 片子)。
  **M2 留下的"要不要等第一帧再起算"在这个片子大小下不需要做**;片子更大、更高分辨率时再看。
- **内存:** Unity 的精确计数器每次运行都不变;RSS 在前几轮从 302 升到 319 MB 后峰值不再上涨,但这是粗指标,**核心自己的堆没有在设备上单独量**
  (Windows 上的 ctypes 测试量过:每个打开/关闭周期不到 1 KB),没有做长时间浸泡,不能据此说"不泄漏"。

## 没覆盖到的(请不要把上面的结论外推到这些)

- **Unity 6000 上的 Android:** 没装 Android 模块(要下载,会先问你),`com.alphaclip.video` 在 6000 的 Android 上没有验证过。你说在用 6000,这个决定还没做(见交接)。
- **AAB / Google Play 的 16 KB 要求:** 只验证了 ELF 层(LOAD 对齐 0x4000)和一个**压缩存放**的开发 APK 的 zip 对齐。没有做 AAB,没有用不压缩存放的 `.so`,没有 Play Console 的检查,
  没有在 16 KB 页的设备或模拟器上加载过(Pixel 6a 是 4 KB 页)。CLAUDE.md 里"要用真实 AAB 验证"这一条仍然开着。
- **固定核类型的基线:** M1 要求"固定核类型、多次重复、记录频率和温度",这次做到了多次重复和电池温度,**没有固定核**,**也没有运行期间的频率**,内核温区读不到。
  要补的话需要新增一次设备运行(例如用 `run-as ... taskset` 固定解码线程,或在核心里加一个固定核的开关),都是对手机的新操作,要你另外同意。
- **GPU 侧耗时、屏幕上的最终画面:** 只量了主线程 CPU 侧的上传/绘制提交;画面正确性读回的是 `Output`,四边形、相机、交换链这一段没有读回,也没有人看过手机屏幕。
  另外 Unity 报的刷新率是 30 而主线程循环跑 57.8 fps,没有深究。
- **规模与素材:** 只有两个合成片(640×360、30 fps);没有真实素材、没有 1080p、没有多路并发、没有长时间浸泡(发热降频的行为不知道)。
- **别的设备和 SoC:** 只有这一台 Pixel 6a。
- **功能:** alpha 渲染(M4)、sidecar(M4)、音频、全局实例数上限与降级、进后台暂停(设计 §9.4,设备上没验证)。
- **Release 构建:** 只有开发构建(带 debuggable 标志、`Development`),没有 Mono / IL2CPP 的 release 对照,没有 stripping 对 P/Invoke 的影响的测试(`link.xml` 之类)。
- 另一类没覆盖:APK 里 StreamingAssets 的整个文件被读进内存(`Open(byte[])`),大文件不适用。
