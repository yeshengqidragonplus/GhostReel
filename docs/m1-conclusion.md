# M1 结论

状态:**已定稿**(2026-11-05,经用户确认)· 对应设计文档 §11 的 M1:核心库 + 命令行小工具,完成标准"与 ffmpeg 参考输出逐帧一致"。
设计决定和相对设计文档的差异见 [m1-notes.md](m1-notes.md);本文只放结论、证据、数据和没覆盖到的东西。

## 一句话结论

**M1 的完成标准达成。** C++17 核心库(C ABI `ac_*`)在 Windows x86_64 和 Pixel 6a(Android arm64,NEON)上,
解码输出与 ffmpeg(`-c:v libvpx-vp9`)**逐字节一致**,覆盖不透明、`native_alpha`、带隐藏帧的超帧、奇数分辨率;
线程化播放器、循环(时钟连续)、seek 都有对 ffmpeg 或理想模型的检查;4200 例(Windows)+ 2200 例(真机,含 1000 例 ASan+UBSan)
畸形输入没有崩溃、卡死或被消毒器报告的问题。**还没有的:** 共享库(`.so` / `.dll`)目标、任何引擎绑定(M2 起)、真实素材。

## 证据

测试片都是自己用 ffmpeg lavfi 合成的,没有第三方素材:M0 的两个(`samples/m0/`:640×360,60 帧,alpha / 不透明)加
M1 的四个边界片(`samples/m1/gen_clips.ps1`)。

| 片子 | 特点 |
|---|---|
| `alpha_native.webm` / `opaque.webm` | 640×360、60 帧、每 30 帧一个关键帧 |
| `opaque_altref.webm` | 两遍编码,**含 5 个隐藏帧**(超帧:一个包里一个隐藏帧加一个可显示帧),60 个包 |
| `opaque_odd.webm` / `alpha_odd.webm` | **321×181 奇数分辨率**(色度平面向上取整),每 15 帧一个关键帧 |
| `alpha_scenecut.webm` | 画面中途硬切、alpha 是静止的圆盘;想制造"两路关键帧错位",**没有成功**(见"没覆盖到的") |

| 检查 | 范围 | 结果 |
|---|---|---|
| `core/tests/test_vs_ffmpeg.py` | Windows,6 个片子 | **281/281** |
| 同一套脚本经 adb 在真机上跑(`core/tests/adb_cli.cmd`) | Pixel 6a(Android 15),普通构建,6 个片子 | **281/281** |

| 同上 | Pixel 6a,ASan+UBSan 构建 | 1000 例,0 崩溃、0 卡死 |

测试脚本实际检查的东西:
- 全部帧与 ffmpeg 独立解码逐字节相同;`info` 与 ffprobe 一致(尺寸、包数、时长)。
- seek:片头之前、片头、帧间、每个关键帧及其前一刻、片尾之后,取出的帧恰好是"目标时刻显示的那一帧"及之后的帧,逐字节一致。
- 线程化播放器:整片预解码后细时钟取帧,每帧恰好一次、按序、0 丢帧;粗时钟(20 ms 到 1 s 步进)取出的帧和丢帧数与"最新到期帧优先"的理想模型完全相等;
  自由运行(队列深度 1/2/4/16)pts 严格递增、字节正确、`decoded == acquired + dropped`;提前关闭不挂死;
  线程化 seek(确定性的、以及解码线程忙时向前向后 seek,seek 之后不能出现过时帧)。
- 循环:交界处 pts 恰好差一个循环周期;seek 到最后一帧再循环时偏移依次累计 +P、+2P;自由运行跨多遍。
- 缺文件、空文件、随机字节、多个截断位置、错误用法:干净失败。

**测试有效性的两个对照:**
- 变异测试:临时去掉解码线程里丢弃过时帧的检查,线程化 seek 的两组测试立刻失败。
- 消毒器对照:一个故意带堆越界和有符号溢出的小程序,用同样的 NDK 参数在真机上编译运行,ASan 和 UBSan 都报告并让进程以 SIGABRT 终止(退出码 134),
  压测脚本会把这种退出码判为崩溃。所以"1000 例插桩运行无报告"是有意义的。

## 真机耗时(Pixel 6a,单个解码线程,640×360)

`ac_get_stats().decode_time_us / frames_decoded`:核心库解码线程自己的耗时,**含彩色解码、alpha 解码和平面拷贝**,不含等待。
队列深度 4(缓冲区复用),用 `taskset` 固定到某一类核,每种配置 5 次,设备已冷却:

| 核 | alpha 片 ms/帧(最小 .. 最大,中位) | 不透明片 ms/帧 | alpha 比不透明多 |
|---|---|---|---|
| 大核 Cortex-X1 | 1.09 .. 1.36,中位 1.29 | 0.89 .. 0.96,中位 0.93 | 约 +39% |
| 中核 Cortex-A76 | 2.19 .. 2.35,中位 2.28 | 1.54 .. 1.62,中位 1.60 | 约 +42% |
| 小核 Cortex-A55 | 4.36 .. 4.81,中位 4.58 | 3.06 .. 3.29,中位 3.18 | 约 +44% |

怎么读这些数字:
- **平面拷贝不是大头:** 临时计时显示每帧拷贝 0.04–0.26 ms(大核:不透明 0.04、alpha 0.14;中核 0.15–0.26;小核 0.11–0.17)。
  核心库比"只解码"的 M0 探针多出的就是这一块加一点胶水。分辨率放大后拷贝按像素数增长,将来如果成为瓶颈,可以考虑直接从 libvpx 的缓冲区上传、少拷一次。
- **这台手机上的耗时抖动很大,只能给范围:** 同一个程序、同一类核,彩色解码单帧在 0.7 到 1.1 ms 之间双峰分布;调频器是 `sched_pixel`;
  连续跑了约 40 分钟测试后读到大核频率上限被降到 2.25 GHz(额定 2.8 GHz),几分钟后恢复。
- **M0 的数字偏乐观:** M0 当时测得大核彩色加 alpha 约 0.83 ms/帧;M1 同一个探针在同样的核上现在测出 1.2–1.3 ms,
  与核心库的 1.1–1.4 ms 基本一致。M0 那次是比较好的一段,不应当作基线。**M3 的性能基线必须固定核类型、多次重复、记录频率和温度,并报告范围。**
- 在 30 fps 下单帧预算是 33 ms,本片在这个分辨率下余量很大;**不要外推到 1080p 或多路并发**,目标规格(§13.2)未定,耗时也没有按像素数验证过。

## 没覆盖到的(请不要把上面的结论外推到这些)

- **共享库:** M1 只产出静态库和命令行。Unity / Godot / Cocos 要的 `.dll` / `.so`(导出 `ac_*`)还没有构建目标,是 M2 的第一件事;
  也还没有验证从 Unity 里加载它(符号可见性、`c++_static`、16 KB 对齐的 `.so` 在 APK 里的 zip 对齐)。
- **素材:** 全是合成片,只有 640×360 和 321×181 两种尺寸,alpha 很平滑;没有真实素材(头发、粒子),没有 1080p / 4K。
  只有 ffmpeg(libvpx-vp9)产出的 alpha WebM;其他编码器的 alpha 写法(例如 BlockAddID、BlockAdditionMapping)没测。
- **关键帧错位:** M0 留下的问题("彩色与 alpha 两路关键帧是否会错位")仍然没有真实样本:`alpha_scenecut` 里画面硬切,libvpx 也没有插关键帧,两路都只在第 0 帧。
  核心对错位的处理(seek 只从"两路都是关键帧"的位置开始,必要时回退到更早的点)按设计实现,但这条路径没有被真实文件走到。
- **内存安全:** ASan/UBSan 只在真机的 arm64 构建上跑,覆盖了套件和 2200 例变异;没有 libFuzzer 那样的覆盖率引导,变异是确定性的。
  已知缺口(见 m1-notes 第 5 点):被篡改的帧头声明很大的尺寸时 libvpx 可能先分配大块内存,压测没有触发。
- **数据竞争:** 没有 ThreadSanitizer(没有在 NDK 或 llvm-mingw 里验证过是否可用);线程化播放器靠上面的并发测试、150 次压力运行和代码审查,不能算被证明。
- **设备和环境:** 只有一台 Pixel 6a;没有低端机、没有其他 SoC;没有长时间浸泡(设计 §10 要求的 1 小时循环、反复创建销毁 1000 次);内存占用未测。
- **多线程解码**(libvpx `threads > 1`)没测;每个实例两个解码器同时的缓存压力没测。
- **sidecar 元数据**(`meta_json`)没有实现(M4),所以 `matrix` / `color_range` / `packed_*` / `keyed` 都还没有。
- **PNG 输出没做:** 设计 §11 把 M1 写成"逐帧输出 YUV/PNG",命令行只输出原始平面 YUV(A)(和 ffmpeg 的 `yuv420p` / `yuva420p` 同布局,便于逐字节比对)。
  PNG 需要 YUV→RGB 的矩阵和范围,它们来自 sidecar(M4),所以放到那时;现在要看图,可以用 ffmpeg 把 `.raw` 转成图片。

## 给后续里程碑的交接

| 事项 | 归属 |
|---|---|
| 共享库目标(Windows `.dll`、Android `.so`),导出 `ac_*`,隐藏其余符号;静态 libc++;16 KB 对齐 | M2 开头 |
| Unity 里加载共享库、纹理上传、播放组件 | M2 |
| 性能基线:固定核类型、多次重复、记录频率温度、报告范围;目标规格定下来之后再测 | M3 |
| 平面拷贝是否要去掉(直接从 libvpx 缓冲区上传) | 看 M3 基线再定 |
| 关键帧错位的真实样本(可能要自己写一个把两路码流分别编码再封装的小工具),以及 `verify` 的检查 | M5 |
| 更强的模糊测试(libFuzzer / 覆盖率引导)、TSan、浸泡测试 | M3 前后,见 m1-notes |
| sidecar 元数据解析与 schema 校验 | M4 |

> **M2、M3 之后的处理结果(2026-11-06 加注,上面的正文是 M1 定稿时的原样):**
> 共享库目标(Windows `.dll`、Android `.so`,隐藏符号、静态 libc++、LOAD 段 16 KB 对齐)——**完成**(M2 做了 `.dll`,M3 做了 `.so`);Unity 里加载、纹理上传、播放组件——**完成**(M2);
> 性能基线——M3 做了应用内、**未固定核**的第一份,**固定核类型的基线仍未做**(m3-conclusion);平面拷贝——640×360 下不成问题(上传约 0.23 ms/张),暂不去掉,1080p 没量;
> 更强的模糊测试、TSan、浸泡测试——M3 **没有做**,仍然开着;关键帧错位的真实样本和 `verify`——仍是 M5;sidecar——仍是 M4。
